# 設定與環境變數

Claude Code 的行為由三層來源決定：環境變數、`settings.json`、以及提詞類的檔案
（`CLAUDE.md`）。三者的載入時機不同，改了沒生效時要先分清楚是哪一層。


## 環境變數在啟動時讀取

環境變數只在程序啟動時讀一次，執行中改沒有作用。這表示要讓某個變數生效，
必須在啟動指令的同一行設定，或是先 export 再啟動：

    VAR=1 claude

或

    export VAR=1
    claude

先結束程式、之後才單獨設定變數再啟動，是最常見的失敗方式 ——
變數留在原本的 shell，新的程序讀不到。寫在 `~/.bashrc` 之類的啟動檔時，
也要確認該檔案在啟動前確實被載入過。

要確認某個程序實際拿到哪些環境變數，直接 dump 它的環境：

    ps eww -p <pid> | tr ' ' '\n' | grep VAR_NAME

這比檢查 shell 當下的狀態可靠，因為它看的是目標程序本身。
若整個輸出都沒有形如 `NAME=value` 的項目，表示讀取權限有問題，
而不是變數不存在，要先確認這點再下結論。


## 設定檔的層級

    ~/.claude/settings.json              使用者層級，所有專案
    <專案>/.claude/settings.json         專案層級，會進版控
    <專案>/.claude/settings.local.json   專案層級，個人覆寫，不進版控

後面的覆寫前面的。修改時務必合併而非替換 —— 陣列型的欄位（權限規則、hook）
直接覆寫會刪掉既有項目。

格式錯誤會讓整個檔案的設定全部失效，而且沒有錯誤訊息。改完用 `jq` 驗證，
順便確認其他既有設定還在。


## 功能開關與副作用

以環境變數提供的開關，往往同時關掉一整條程式路徑，而不只是表面上那個功能。
關閉某個行為之前，值得先確認還有什麼共用同一條路徑。

實例：關閉終端機標題的自動更新後，`/rename` 也一併失去改標題的能力 ——
它走的是同一個寫入路徑。設定檔裡另有一個控制「`/rename` 要不要改標題」的欄位，
但那個欄位擋不住上層的環境變數。

這類相依關係不會出現在文件裡，通常要實測或讀原始碼才會發現。
關掉某個功能後，把相關功能都試一遍是值得的。


## 提詞類檔案

`CLAUDE.md` 是給模型讀的內容，不是設定。它可以影響模型的行為傾向，
但無法讓系統在特定事件自動執行動作 —— 那需要 hook。

需要「每次都自動做某事」時，判斷標準是：這件事該由模型決定要不要做，
還是不管模型怎麼想都必須發生。前者寫提詞，後者寫 hook。
