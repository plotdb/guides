# Context 目錄結構指南

定義 `context/` 目錄下各子目錄的用途與使用方式。


## context/shared

共用上下文資訊，由外部 repo 匯入，通常以 symlink 方式建立。

若需調整其中的原則，應找來源 repo 修改，並可先與 user 確認。


## context/memo

開發者的人工筆記. 亦可參考,  但除非有明確指示, 不然應避免修改此處的內容.


## context/project

存放專案相關資訊，結構如下：

 - `index.md` — 基本資訊與 quick guide 摘要
 - `initiative/` — 初期草案與構想，見下方說明
 - `logs/` — 工作記錄，以 `yyyymmdd-<brief>.md` 命名
 - `tasks/` - 工作項目, 以 `yyyymmdd.md` 或 `<task-name>.md` 命名
 - `ref/` — 參考資料, 見下方說明
 - `spec.md` — 定義預計系統的規格與設計 ( TBR，見下方說明 )
 - `features.md` — 說明目前系統已有的機制與功能 ( TBR，見下方說明 )

其它檔案可視專案需求自行規劃。

### 通用慣例(logs/、tasks/ 等所有子目錄適用)

 - 狀態子資料夾:進行中的檔案直接放根層,其餘依狀態歸入子資料夾。常見狀態:
   - `todo/` — 待處理、尚未開始
   - `done/` — 已完成
   - `hold/` — 擱置、待條件成熟
   - `drop/` — 決定不做(保留脈絡供日後參考)
 - 年份歸檔:較久的資料移入年份子資料夾, 如 `20250101-foo.md` → `2025/0101-foo.md`
 - 兩者並用時先狀態再年份:`tasks/done/2025/0101-foo.md`

### initiative/ — 初期草案

放構想、草案與尚未定案的討論。命名比照 `logs/`，以 `yyyymmdd-<brief>.md` 為主，
一則草案含多個檔案時用同名資料夾。

它與其它子目錄的差別在於：程式碼還不存在時，草案暫時就是 source of truth ——
你是照著它做事的。`ref/` 收的是素材，被動、供查閱；`initiative/` 是當下的行動依據。

關鍵規則是落地後即凍結：內容不再更新，只改狀態。有了這條，它就與 `logs/` 同性質 ——
宣稱的是「某天我們打算這樣做」，是時點而非現況，程式再怎麼改都不會讓它變假。
少了這條，它會退化成另一份需要持續維護、且必然過期的 spec。

通用慣例的狀態子資料夾直接適用：

 - `initiative/done/` — 已落地，成果在程式碼與 `logs/` 裡
 - `initiative/drop/` — 討論後決定不做，保留脈絡
 - `initiative/hold/` — 方向可行但時候未到

其中 `drop/` 特別值得留。「我們考慮過 X 但否決了」是原始碼編碼不了的資訊之一，
而它通常大到塞不進註解。

`initiative/`、`tasks/`、`logs/`、`ref/` 合起來是一條承諾程度的軸：

 - `initiative/` — 還在想，可能不做
 - `tasks/` — 決定要做
 - `logs/` — 做了什麼
 - `ref/` — 不屬於任何一次工作的素材


### ref/ — 參考資料

放不屬於任何一次工作的素材:討論串、腦力激盪、外部建議、被取代的舊設計與舊 spec。

與 `logs/` 的差別在於有沒有時間軸。log 記「某天做了什麼」,有前後順序,所以用狀態
與年份分類;ref 的內容沒有這條軸,它是**素材**,屬於它所描述的主題。因此不要把
brainstorm / draft / discussion 這種「種類」目錄開在 `logs/` 底下 —— 那會讓狀態與
種類兩條軸混在同一層,看到 `logs/brainstorm/foo.md` 也答不出它做完了沒。

ref 可以開在兩種位置,兩者的命名要求不同。

**`context/project/ref/`** —— 根層的 ref, 沒有 scope, 什麼主題都收, 只會愈長愈大。
這裡**預設以 `yyyymmdd-<name>` 命名**, 單一檔案用 `.md`, 一則素材含多個檔案時用
同名資料夾。日期是素材產生的時間, 不是歸檔的時間。

日期開頭在這裡是關鍵:手工維護的目錄清單一定會過期, 而過期的清單比沒有清單更糟;
檔名帶日期則讓目錄列表自己就是索引, 依時間排好, 永遠不會失準。這正是 ref 不變成
垃圾堆的機制 —— 所以不必為它維護逐檔說明, 對應的 index 只要一句「參考與備查資料,
有需要自行翻閱」即可。

**主題資料夾下的 ref** —— 主題本身已經有自己的資料夾時(如 `features/credit/`),
ref 就開在該主題底下(`features/credit/ref/`), 不必集中到根層。這裡已經被父層
scope 限縮過, 光是路徑就回答了「這是關於什麼的」, 所以命名可以寬鬆, 檔名講清楚
它是什麼即可。

同一個主題累積出第二批 ref 時再用 `yyyymmdd-<intent>/` 分批
(如 `ref/20260801-draft-and-old-design/`), 用資料夾標示這批的意圖與時間。
只有一批時不必先分。

被取代的文件留在 ref 而不是刪掉,是因為讀舊 log 或舊 migration 時需要對照當時的
名稱與結構。但務必在檔案開頭寫明它已失效、以及現行的權威在哪裡 —— 這是逐檔要做
的事,也是唯一要做的事,否則下一個人會把它當成現況。

### spec.md 與 features.md ( TBR )

這兩份文件的定位待重新檢討。目前仍可沿用，但在結論出來前不建議投入太多維護成本。

若內容較多，可分別延伸為 `spec/` 或 `features/` 資料夾，但需在對應的 md 檔中說明
其結構。

疑慮是這兩份文件宣稱的是「系統現在長怎樣」，而這句話的真偽會隨每次 commit 改變。
它們因此需要跟著每次改動維護，但實務上不會 —— 改程式的人沒有動機去更新一份與執行
無關的檔案。過期而看起來仍具權威的文件，比沒有文件更糟。

一個可用的判準：這份文件與程式碼不一致時，會去改哪一邊？答案是「改文件」的話，
它就是衍生物，就會過期。`logs/` 答不出這個問題，因為它記的是「某天做了什麼」，
是時點而非現況，程式再怎麼改都不會讓它變假。

但源碼也有編碼不了的東西，主要是三類：

 - 被否決的選項。程式碼只呈現最後採用的做法，看不出哪些替代方案評估過並否決
 - 失敗的嘗試。成功的程式碼裡沒有失敗的痕跡，後人容易再踩一次
 - 外部事實。程式依賴的執行環境、第三方工具行為、格式約定，程式本身不記載

目前傾向是這三類寫在決策發生的那一行旁邊 ( 也就是原始碼註解 )，而不是集中到一份
獨立文件。理由是註解與它解釋的對象住在一起：改那段程式的人一定會看到它，刪那段程式
時它也一起被刪 —— 這是獨立文件拿不到的保證。

若此方向成立，`context/project` 的分工會變成：`initiative/` 承擔尚無程式碼階段的
草案，`logs/` 承擔歷史與決策過程，原始碼註解承擔「為什麼這樣寫」，`index.md` 退化成
一份只指路不描述內容的索引，而 `spec.md` 與 `features.md` 不再維護。

專案初期無程式碼可承載的疑慮已由 `initiative/` 處理：它扮演該階段的 source of truth，
但落地後即凍結，不轉為長期維護的 spec。

尚未定案的部分：

 - `index.md` 若只指路，與各 repo 的 README 如何分工
 - 對外的 README 與對內的 context 之間，界線畫在哪


## context/cached

存放暫時性檔案，例如臨時呈現資料或說明用的 HTML 等。

`context/cached` 預設不進 git，建議在 `.gitignore` 加入：

    context/cached
